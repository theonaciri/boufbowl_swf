# Cheating and abuse review

Reviewed 2026-10-14 after adding CPU class-power decisions. This is a source
review, not a penetration test. Findings below describe current code and proposed
work. Seed privacy and ranked-result separation were implemented after this
review; the remaining hardening proposals below are still outstanding.

## Trust model and existing protections

A competitive game must use a trusted backend. A player who controls their own
server/database can alter its rules, results and records; those results must not
be imported into a public ladder as authoritative. Editing a SWF or submitting
custom HTTP requests must never grant authority over public match state.

The current backend computes movement, fights, catches, goals and class effects;
clients submit orders and acknowledge presentation. It checks sessions, roster
ownership, placement zones, roles, three valid element slots, phases, turns,
one power per team, caster exclusivity and power availability/usage. Match
characteristics come from server configuration, and match-local character IDs
are generated by the server. Confirmed orders are immutable. Stable request IDs
make retries idempotent; match-result inserts prevent duplicate reward delivery.
Replay verification checks recorded engine events and final state hashes.

Local accounts hash passwords using PBKDF2; session tokens are hashed in the
SQLite session table. Password endpoints require TLS for remote callers.
Chat has a one-second sender limit, reports a one-minute reporter limit, and
private messages honor blocks. These are useful protections, not comprehensive
abuse controls.

## Implemented first fixes

- Active replay exports are playback-only (`records: []`, `audit_available: false`)
  and cannot perform full verification. Full audits are released after completion.
- Every resolved turn draws an independent private seed. Completed records
  retain their seeds for verification.
- Only human normal/tournament queue matches affect ranked rating and ranked
  W/D/L. CPU and challenge outcomes stay in separate practice/casual counters
  and match history. Only tournament-queue matches score tournament points.
- Schema 8 starts fresh development data and clears incompatible databases.
  Legacy archives/migrations were removed; result reward retries remain idempotent.

These fixes do not prevent alternate accounts from colluding inside ranked queues;
ranked eligibility and repeated-pair controls remain separate work.

## Findings and priorities

| Priority | Area | Current risk | Recommended change |
|---|---|---|---|
| Fixed | Active replay / randomness | Previously, active exports disclosed seeds derived from a reversible shared match seed. Live exports now omit raw records, and new turn seeds are independent. | Stop publishing seeds and full audit records during active matches. Generate independent private per-turn seeds, or derive them from a server-only cryptographic secret. Release complete replay audits after completion. Preserve old seed rules for historical replay verification. |
| Fixed | Competitive rating | Previously, CPU games and challenges changed competitive rating. They now have separate non-ranked ledgers; tournament points require queue provenance. | Classify matches as practice, casual or ranked. CPU/practice results should stay in history but not competitive rating. Restrict ranked rewards to eligible human matchmaking, and define eligibility before introducing prizes. |
| P1 | Collusion / alternate accounts | Anonymous profiles and local accounts are inexpensive to create. Repeated opponents and surrender/concede flows can be used to manufacture wins or tournament points. Busy-player checks prevent simultaneous pairings, not repeated farming of the same pair. | Keep anonymous casual play. Add stronger ranked eligibility, pairwise reward limits, cooldowns and match-duration checks. Detect repeated reciprocal wins, account clusters and rapid forfeits; require review before penalties. Separate tournament entry eligibility from ordinary queue membership. |
| P1 | Session theft | Remote password login requires HTTPS, but authenticated commands, polls and device sessions can still run over plaintext HTTP. Bearer sessions last one year. | Enforce HTTPS for every remote API route, shorten access-token lifetimes, rotate credentials and support operator revocation. Preserve loopback HTTP for local development. Never include tokens in logs or exported replays. |
| P1 | Resource exhaustion | The threaded HTTP service has a body-size cap but no general endpoint/concurrency quotas or request-read timeout. Account password hashing, broad queries, many queued accounts and replay verification can consume CPU. Simulation and verification hold the shared database lock. | Put a bounded reverse proxy in front of public service; enforce read timeouts and per-IP/account/global quotas. Bound queued players/spectators, cache replay exports, restrict verification to operators or background jobs, and move expensive work outside long database transactions. |
| P1 | Intentional stalling | A client can withhold introduction/resolution acknowledgements until their deadlines. Resolution currently waits up to 300 seconds. A player can repeatedly time out or disconnect. | Treat acknowledgement as presentation feedback only. Add reconnect grace, bounded playback wait and escalating abandonment policy. Log actual latency/loading separately from deliberate repeated stalls. Never accept an acknowledgement as a new result or goal. |
| P2 | Chat / social abuse | Per-profile message/report limits can be bypassed using many profiles. Friend/challenge spam and naming impersonation have no equivalent broad quotas. Audited moderator kick/ban/mute and revocation now exist, but anonymous alternative profiles bypass profile-only sanctions. | Add account/IP/global buckets, friend/challenge caps, duplicate-content controls, moderator roles, temporary mutes/bans, appeals and action audit logs. Escape untrusted names/messages in every HTML-rendered client surface; client rendering needs a separate content-injection review. |
| P2 | Spectating / assistance | Players can use another account to spectate or share live information. Live exports include completed-turn playback; audit records/seeds remain private until completion. | Decide the ranked spectator policy: delay broadcasts and audit data, forbid participant-linked spectator accounts where defensible, and disclose what opponents/spectators can see. Keep unresolved orders private. |
| P2 | Bots / external solvers | A program can submit legal orders and optimize them using the published rules. Server validation cannot distinguish a valid bot order from a valid human order. | Use behavioral evidence, rate controls and a declared competition policy. Flag suspicious consistency or instant decisions for review. Client checksums or obfuscation are not a reliable enforcement boundary. |
| P2 | Storage / evidence | Commands, events, chat, reports and turns accumulate without retention quotas. Anonymous account floods can grow the database. Replay hashes prove reproducibility, not the provenance of an externally supplied replay. | Set retention/storage budgets and archive policy. Sign completed replay manifests with a server key when authenticity matters. Store moderation evidence with restricted access and defined retention. |

Do not ban solely because two players share an IP, submit quickly, disconnect, or
use unusual tactics. Those are signals with legitimate explanations. Keep
ranked eligibility, detection, investigation and punishment separate.

## Implementation order

1. **Completed:** close the active-replay seed disclosure and replace future-match seed
   derivation; add regression tests proving active clients receive no seeds or
   unresolved orders.
2. **Completed:** split competitive rating from CPU/casual matches and apply the same policy to
   tournament scoring. Test practice wins, challenges, repeated pairs, retries
   and forfeits.
3. Apply TLS to all remote authenticated routes, add request/concurrency limits
   and bound expensive replay verification.
4. Add structured security events: profile/match/turn, rejected command code,
   endpoint, timestamp, timeout outcome and moderation action. Avoid raw tokens,
   passwords and unnecessary message content in logs.
5. Add ranked eligibility, collusion flags and spectator delay. Moderator roles,
   kick/ban/mute, revocation, protected authorization and audit UI are now implemented.
   Test bans across queue, challenges, spectating and chat; review false positives.

Existing relevant tests cover ownership, normalized statistics, invalid phases,
immutable orders, duplicate-result protection, account rate limits, blocks,
spectator acknowledgements and deterministic replays. The gaps above need
explicit adversarial regression tests before exposing a public competitive server.
